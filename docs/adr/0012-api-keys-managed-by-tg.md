# ADR-0012 — API key ของระบบอื่นอยู่ในฐาน · TG ออกและถอนเองที่ `/admin/api-keys`

วันที่ 11 พฤศจิกายน 2569 · สถานะ: ใช้อยู่ · แทนส่วน "ทะเบียนใน env" ของ spec §6

เดิมทะเบียน consumer ของ `/api/v1/*` อยู่ใน env `WORKTRAIN_API_CONSUMERS` (`ชื่อ:read:<sha256>` แบบ WorkHR)
และออก key ด้วย `npm run api:new-key` บนเครื่องนักพัฒนา — ออก หมุน หรือถอน key ต้องมีคนเข้า Vercel แก้ env แล้ว redeploy
เจ้าของต้องการให้ TG ทำได้เองจากหน้าจอ

**ตัดสินว่า**
- ทะเบียนย้ายไปตาราง `api_consumers` (migration 0009) · env `WORKTRAIN_API_CONSUMERS` และสคริปต์ `api:new-key` เลิกใช้
- **TG เท่านั้น**ที่ออกและถอน key ที่ `/admin/api-keys` — แต่ละ key มี**ชื่อ key** (บังคับ · ภาษาไทยได้ · ≤ 60 ตัว — migration 0010) แยกจาก**ระบบที่ใช้** (`workhr` · อังกฤษตัวเล็ก · ใช้ใน log) · เห็นชื่อ key · ระบบ · 4 ตัวท้ายของ key · ใครออก · ใช้ล่าสุดเมื่อไร · สถานะ
- เก็บแค่ sha256 ของ key · key เต็ม (`wtr_` + สุ่ม 256 บิต) แสดงบนจอ**ครั้งเดียว**ตอนออก ผ่าน state ของ server action — ไม่ลง URL ไม่ลง log
- ชื่อเดียวกันมีได้หลาย key — หมุน key = ออกใหม่ → ปลายทางเปลี่ยน → ถอนตัวเก่า ไม่มีช่วงที่ปลายทางใช้ไม่ได้
- ถอนแล้วเปิดคืนไม่ได้ ไม่มีการลบแถว (เหลือไว้ดูย้อนหลังว่าใครออก/ถอนเมื่อไร)
- scope ยังมีแค่ `read` — ฐานบังคับด้วย CHECK

## เหตุผล

1. **ถอน key ต้องเร็ว** — key รั่วแล้วต้องรอคนที่มีสิทธิ์ Vercel แก้ env + redeploy คือช่วงที่ข้อมูลเปิดอยู่ · ในฐานถอนแล้วมีผลคำขอถัดไป
2. **TG ดูแลระบบอยู่แล้ว** (ADR-0011 · `/admin/*`) — ไม่ควรต้องพึ่งนักพัฒนาเพื่อเปิดให้ WorkHR หรือระบบใหม่ในเครือ
3. **เห็นว่า key ไหนยังถูกใช้** (`last_used_at` อัปเดตไม่เกินชั่วโมงละครั้ง) — ถอนตัวเก่าได้มั่นใจว่าไม่มีใครใช้แล้ว
4. **ค้นด้วย hash ตรง ๆ** แทนเทียบทีละตัวแบบเวลาคงที่ — key สุ่ม 256 บิต รู้เวลาที่ใช้ค้นก็เดา key ไม่ได้

## ไม่เลือก

- **เก็บทั้ง env และตาราง** — สองที่ให้ตรวจ และถอนที่หน้าจอแล้วยังเหลือใน env ได้ · env ไม่เคยตั้งบน production จึงไม่มีอะไรต้องย้าย
- **เข้ารหัส key แล้วแสดงซ้ำได้** — ฐานรั่ว = key รั่ว · ทำหายก็ออกใหม่ได้ในไม่กี่วินาที
- **ให้ผู้สร้างหรือหัวหน้าออก key** — key อ่านสถานะการเรียนของทุกคนได้ ต้องอยู่กับคนดูแลระบบ
